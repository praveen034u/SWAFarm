- [x] KiCad MCP editing-tool defects found and worked around — 2026-07-30, during `01_power` capture:

- [x] Schematic-file structure gotcha found — 2026-07-31, during `06_Relay` bulk capture (66 new components, generated by script and spliced directly into the `.kicad_sch` rather than placed one-by-one via MCP, since per-component tool calls were impractical at this scale): `(lib_symbols ...)` closes far earlier in this file than the top-level `(sheet_instances ...)` block appears — a large run of legacy verbose-format placed symbols (from early `01_power`/`02_MCU` capture) sits between the two. Splicing new library-template content in based on adjacency to `(sheet_instances ...)` lands inside the placed-symbol region instead, and even after locating the real closing paren (via a string-aware, quote-respecting paren-depth counter — a naive counter can be fooled by parentheses inside property text like Description/Datasheet fields), new content must be inserted **before** that closing paren, not after — inserting after silently places new symbol templates outside `lib_symbols` entirely. Both mistakes produced files that parsed fine under the MCP server's own lenient parser (`get_schematic_info` reported the correct component count either way) but that real `kicad-cli sch erc` flatly refused to load ("Failed to load schematic", no line or reason given). Fix/process: locate `lib_symbols`' true end with a string-aware paren counter, insert new template blocks immediately before that closing paren, and always verify with real `kicad-cli` — never trust the MCP parser alone — before trusting a bulk splice.
- [x] New `add_component_from_library` defect found — 2026-07-31, during `04_RS485` capture: for stock symbols that use KiCad's `extends` inheritance (e.g. `Interface_UART:THVD1450D` extends `MAX481E` extends `LTC2850xS8`), the tool only copies the named symbol's own (often pin-less) block into the schematic's `lib_symbols` cache — it does **not** walk the inheritance chain to pull in the base symbol(s) that actually define the pins/graphics, and it does not warn that the resulting definition is incomplete. The placed instance also only gets as many `(pin ...)` entries as the tool's (wrong) pin count, not the true pin count. Symptom: `add_component_from_library`'s own success message reports an implausibly low pin count (e.g. "2 pins detected" for an 8-pin IC) — treat that as a red flag requiring manual verification via `get_symbol_details()` before wiring. Fix: replace the schematic's cached `lib_symbols` entry with a self-contained definition (no `extends`) carrying the real pins/graphics copied from the ultimate base symbol, and correct the placed instance's pin list to match. Produces one expected, harmless `lib_symbol_mismatch` ERC warning versus KiCad's own stock copy.
- [x] Grid-alignment process error found and fixed — 2026-07-31, during `08_BatterySolar` bulk capture: hand-picked "round number" origin coordinates (e.g. `(200.00, 900.00)`) for new-component placement, forgetting that convenient decimal millimeter values are very often *not* exact multiples of 1.27mm (the KiCad connection grid) — the same class of mistake already documented from `02_MCU`. First ERC pass showed 70 new `endpoint_off_grid` warnings as a result. Fixed with a targeted regex pass snapping only origin-variable assignments (identified by naming convention, e.g. `*_O = (x, y)`) to the nearest 1.27mm multiple — deliberately excluding any coordinate copied from a real, already-existing component pin (e.g. the verified MCU pin used for the battery-voltage ADC connection), since blind-snapping those would silently disconnect the label from the actual pin it needed to reach. Lesson: when bulk-generating placements programmatically, choose grid-valid origins (multiples of 1.27mm, ideally 2.54mm) at the point of picking coordinates, not as a post-hoc fix — and never apply an automated snap/transform across a script without first checking whether any of its coordinates are copied from real, external, must-stay-exact positions.
- [x] PCB footprint placement done via `pcbnew` Python scripting, not direct-file-splice — 2026-07-31, during `09_PCBFloorplan`. No MCP tool exists for PCB footprint placement, board-outline creation, or layer-stack setup (confirmed by searching the full tool list before starting), and `.kicad_pcb` footprint blocks are far larger/more error-prone to hand-author than schematic symbols (full pad/courtyard/silkscreen geometry embedded per placed instance, not a template+instance split). Used KiCad 10's own bundled Python (`C:\Program Files\KiCad\10.0\bin\python.exe`, `pcbnew` module — the same interpreter the MCP server itself runs on) via `pcbnew.FootprintLoad()` to pull real, verified footprint geometry straight from the system libraries, `pcbnew.CreateEmptyBoard()`/`SetCopperLayerCount(4)`/`PCB_SHAPE` for board setup, and per-pad `SetNet()` (matched against a parsed netlist XML) so placed pads carry real net membership for the next milestone's ratsnest/DRC — all far more reliable than the raw-S-expression-splice technique used for schematic work. Separately, a footprint-sizing lesson: the first placement pass estimated component spacing from assumption (e.g., schematic-visual connector pitch) rather than measured geometry, producing 38 courtyard overlaps, 32 net-shorting collisions, and 4 co-located mounting holes on first DRC. Root cause: `footprint.GetBoundingBox()` includes the silkscreen reference-designator text and can overstate a small connector's real size by 3x (e.g. a 3-pin terminal block measured 53mm "wide" by bounding box but only 16mm by courtyard) — the *courtyard* layer (`F.CrtYd`/`B.CrtYd`), not the full bounding box, is the correct measure for real-world spacing. Fixed by querying courtyard geometry directly for every unique footprint before re-placing, then iterating against real `kicad-cli pcb drc` output (not visual inspection) to resolve the remaining handful of collisions. Lesson: for PCB placement work, always measure real courtyard geometry via the API before choosing spacing — the same "verify against real data, don't guess" discipline already applied to library symbols, now applied to physical footprint geometry.
